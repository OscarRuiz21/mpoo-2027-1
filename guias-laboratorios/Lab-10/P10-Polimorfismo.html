En la P9 ya usaste abstract, extends y @Override. Hoy ves para qué sirven: para que el juego dé una orden y cada objeto responda a su manera. Eso se llama polimorfismo.

Qué es el polimorfismo

Polimorfismo quiere decir «muchas formas». Una misma orden, h.golpear(), y cada objeto responde con lo suyo: la espada da un tajo, el arco dispara dos flechas, el bastón lanza un hechizo. Quien da la orden no pregunta qué herramienta tiene enfrente.

Para que eso funcione hacen falta tres ingredientes. Los tres aparecen en el código de hoy:

IngredienteQué esEn esta práctica
1 · La clase base dice quéUna clase abstracta declara los métodos que toda hija debe tener, sin decir cómo: public abstract String grito();Herramienta, con grito() y golpear()
2 · Cada hija dice cómoCada clase hija escribe esos métodos a su manera, con @OverrideEspada, Arco y Baston: tres gritos y tres reglas de golpe
3 · El juego llama sin preguntarUna variable del tipo base, Herramienta h, puede guardar cualquier hija. Al llamar h.golpear(), Java mira el objeto, no la variable, y corre el método de su clasePersonaje.atacar y el for de Comparar

Parte A · Ejemplo guiado: la clase base y su primera hija

Este ejemplo hace los tres ingredientes con una herramienta, el arco. Síguelo en orden y escríbelo en tu proyecto: cada paso trae el código completo y el concepto que aplica. En el paso A4 compruebas que funciona. En la Parte B repites el patrón con la espada y el bastón.

A1 · La clase base dice qué: Herramienta se vuelve abstracta

clase abstractamétodo abstractoconstructor protected

En el juego ya no existe «una herramienta» a secas: toda herramienta es espada, arco o bastón. Por eso Herramienta se vuelve abstracta, como Personaje en la P9: sirve para agrupar a sus hijas, no para crear objetos. Así queda tu Herramienta.java completo; lo nuevo son la primera línea, el protected del constructor y los dos métodos abstractos:

package mazmorra;

// Ya no existe "una herramienta" a secas: toda herramienta es una
// espada, un arco o un baston. Por eso la clase es abstracta.
public abstract class Herramienta {
    private final String nombre;
    private final int danio;
    private int durabilidad;

    protected Herramienta(String nombre, int danio) {
        this.nombre = nombre;
        this.danio = entre(danio, 1, 50);
        this.durabilidad = 100;
    }

    // 1. GRITO: cada herramienta suena distinto al atacar
    public abstract String grito();

    // 2. GOLPE: cada herramienta decide cuanto dano hace un golpe
    public abstract int golpear();

    public String getNombre() {
        return nombre;
    }

    public int getDanio() {
        return danio;
    }

    public int getDurabilidad() {
        return durabilidad;
    }

    public boolean estaRota() {
        return durabilidad == 0;
    }

    // rota no hace dano; si no, se desgasta un punto
    public int usar() {
        if (estaRota()) {
            return 0;
        }
        durabilidad--;
        return danio;
    }

    public void reparar() {
        durabilidad = 100;
    }

    private int entre(int valor, int min, int max) {
        return Math.max(min, Math.min(max, valor));
    }
}
  • Un método abstracto no tiene cuerpo: termina en ;. Dice «toda herramienta sabe gritar y golpear», pero no dice cómo. Cada hija está obligada a escribirlo; si no, no compila.
  • usar() sigue igual que en la P9: desgasta un punto y devuelve el daño. golpear() es nuevo: cada hija decide cómo convierte un uso en un golpe.
  • El constructor pasa a protected porque ya solo lo llaman las hijas, con super(...).

Desde este momento no se pueden crear objetos Herramienta. Por eso el .zip trae un Main nuevo: el de la P9 hacía new Herramienta("Espada", 20), y si lo compilas sale:

A2 · La hija dice cómo: el Arco

herencia (extends)super(...)sobrescritura (@Override)

Crea src/mazmorra/Arco.java:

package mazmorra;

public class Arco extends Herramienta {
    public Arco(int danio) {
        super("Arco", danio);
    }

    @Override
    public String grito() {
        return "dispara dos flechas";
    }

    // solo el arco tiene flechas: Herramienta no sabe de esto
    public int getFlechas() {
        return 2;
    }

    // dos flechas: el arco se usa dos veces en un solo golpe
    @Override
    public int golpear() {
        return usar() + usar();
    }
}
  • El constructor recibe solo el daño y le pasa a super el nombre "Arco". El daño se ajusta de 1 a 50 en Herramienta, como en la P9.
  • Los dos @Override son la respuesta del arco a las dos obligaciones: su grito y su regla de golpe. El arco dispara dos flechas: usa el arco dos veces en un solo golpe, así que pega el doble y se desgasta dos puntos.
  • getFlechas() es un método que solo tiene el arco: Herramienta no sabe de flechas. Lo vas a necesitar en la Parte D, donde se ve cómo llegar a él desde una variable Herramienta.
  • usar(), getDanio() y lo demás no aparecen: el arco los hereda tal cual.

Si a una hija le falta uno de los dos métodos, no compila. Por ejemplo, sin grito():

saleArco.java:3: error: Arco is not abstract and does not override abstract method grito() in Herramienta

Y si lo escribes sin public, sale attempting to assign weaker access privileges; was public: una hija no puede cerrar lo que la madre dejó abierto.

A3 · El juego llama sin preguntar: el personaje carga una herramienta

agregaciónreferencia de la clase baseenlace dinámico

En la parte 2 el inventario desaparece: cada personaje carga una sola herramienta, la de su tipo. Borra Inventario.java y, en Personaje, cambia el atributo inventario por este y quita el new Inventario() del constructor:

private Herramienta herramienta;       // agregacion: se forja afuera

Luego cambia getCuantasHerramientas() y getHerramienta(i) por un solo getHerramienta(), y deja equipar y atacar así (lo demás de atacar no cambia):

    public Herramienta getHerramienta() {
        return herramienta;
    }

    // una sola herramienta: la nueva reemplaza a la anterior
    public void equipar(Herramienta h) {
        this.herramienta = h;
    }

    public void atacar(Personaje objetivo) {
        if (!estaVivo() || herramienta == null) {
            return;
        }
        int base = herramienta.golpear();   // P10: la herramienta decide
        if (base > 0) {
            objetivo.recibirDanio(calcularDanio(base));
        }
    }
  • La herramienta se forja afuera y llega por equipar: es agregación, como en la P9. Si equipas otra, reemplaza a la anterior.
  • El atributo herramienta es una variable de tipo Herramienta: el personaje no sabe si carga un arco o una espada. Cuando llama a herramienta.golpear(), Java mira el objeto y corre el golpear de su clase. Eso es el enlace dinámico: el método se decide por el objeto, no por el tipo de la variable.

Parte C · Sin y con polimorfismo

referencia de la clase baseinstancias de las clases derivadasenlace dinámico

Este es el momento de la práctica. Vas a ver el mismo trabajo hecho de dos maneras: una que pregunta qué es cada herramienta y otra que no pregunta nada.

C1 · El archivo completo

Este es Comparar.java tal como viene en el .zip. Léelo completo antes de escribir:

package mazmorra;

// El mismo recorrido dos veces: primero preguntando que es cada
// herramienta, luego sin preguntar.
public class Comparar {
    public static void main(String[] args) {
        System.out.println("-- Sin polimorfismo --");
        sinPolimorfismo(arsenal());
        System.out.println("-- Con polimorfismo --");
        conPolimorfismo(arsenal());
    }

    // un arreglo del tipo base con objetos de tres clases distintas
    static Herramienta[] arsenal() {
        return new Herramienta[] {
            new Espada(20), new Arco(15), new Baston(10)
        };
    }

    // el juego pregunta que herramienta es cada una y decide por ella
    static void sinPolimorfismo(Herramienta[] arsenal) {
        for (Herramienta h : arsenal) {
            String grito;
            int golpe;
            if (h instanceof Espada) {
                grito = "lanza un tajo";
                golpe = h.usar();
            } else if (h instanceof Arco) {
                grito = "dispara dos flechas";
                golpe = h.usar() + h.usar();
            } else if (h instanceof Baston) {
                grito = "lanza un hechizo";
                golpe = h.getDanio();
            } else {
                grito = "no se que es esto";
                golpe = 0;
            }
            imprimir(h, grito, golpe);
        }
    }

    // el juego solo da la orden; cada herramienta responde con lo suyo
    static void conPolimorfismo(Herramienta[] arsenal) {
        // TU CODIGO: un for-each sobre arsenal que, por cada h, llame a
        // imprimir(h, h.grito(), h.golpear()). Sin ningun instanceof.
    }

    static void imprimir(Herramienta h, String grito, int golpe) {
        System.out.println(h.getNombre() + " " + grito + ": golpe de "
                + golpe + ", durabilidad " + h.getDurabilidad());
    }
}

Tiene cinco partes:

ParteQué hace
mainCorre el recorrido dos veces: primero sin polimorfismo y luego con polimorfismo.
arsenal()Crea un arreglo del tipo base, Herramienta[], con objetos de tres clases distintas: una espada, un arco y un bastón. Es justo lo que pide el manual: una referencia de la clase más general e instancias de las derivadas.

conPolimorfismoLo escribes tú. Hace lo mismo, pero sin preguntar.

Parte D · Los moldes

upcastinstanceofdowncast

D1 · La teoría: dos tipos en cada línea

En Herramienta h = new Arco(15); hay dos tipos, y no son lo mismo:

El tipo de la variableEl tipo del objeto
En el ejemploHerramienta, lo que va a la izquierdaArco, lo que va después del new
Quién lo mirael compilador, al hacer javacJava, al correr el programa
Qué decidequé métodos puedes llamar: solo los que tiene Herramientacuál versión corre: la del arco
¿Cambia?no, se fija al declararlala variable puede apuntar después a otro objeto

Por eso h.grito() compila (toda herramienta grita) y corre el grito del arco. Pero h.getFlechas() no compila, aunque el objeto sí sea un arco: el compilador solo ve una Herramienta, y no toda herramienta tiene flechas.

A cambiar el tipo de la variable se le llama cast o moldeo. Hay dos direcciones:

Upcast: hacia arribaDowncast: hacia abajo
Va dela hija a la base: Arco → Herramientala base a la hija: Herramienta → Arco
Cómo se escribesolo, sin nada: Herramienta h = new Arco(15);con el tipo entre paréntesis: Arco a = (Arco) h;
¿Puede fallar?nunca: un arco siempre es una herramientasí: una herramienta puede no ser un arco
Para qué sirvetratar a todas igual, como en el arreglo de la Parte Cusar lo que solo tiene la hija, como getFlechas()

Como el downcast puede fallar, antes se pregunta con instanceof: h instanceof Arco da true si el objeto es un arco (o una hija del arco) y false si no. Pregunta por el objeto, no por la variable.

D2 · Los moldes en código

Para este ejemplo, el Arco tiene un método que solo él tiene, getFlechas(): cuántas flechas dispara. Está en tu Arco del paso A2. Este es Moldes.java:

package mazmorra;

// La variable es de un tipo; el objeto puede ser de ese tipo o de un hijo.
public class Moldes {
    public static void main(String[] args) {
        Herramienta h = new Arco(15);           // 1 upcast: automatico
        System.out.println("1 " + h.grito());   //   manda el objeto

        // h.getFlechas();                      // 2 no compila

        System.out.println("3 " + (h instanceof Arco));
        System.out.println("3 " + (h instanceof Espada));

        Arco a = (Arco) h;                      // 4 downcast: se escribe
        System.out.println("4 flechas: " + a.getFlechas());

        // Espada e = (Espada) h;               // 5 compila, pero truena
    }
}
java -cp out mazmorra.Moldes
# corre los moldes (ya está compilado con lo demás)
debe salir1 dispara dos flechas 3 true 3 false 4 flechas: 2
  • 1, upcast: la variable es Herramienta y el objeto es un Arco. El grito es el del arco: manda el objeto.
  • 3, instanceof: el objeto es un arco (true), no una espada (false).
  • 4, downcast: (Arco) h da una variable de tipo Arco, y con ella sí puedes llamar a getFlechas(). Funciona porque el objeto sí es un arco.
