Repaso: polimorfismo

⏱ ~5 min
Lo esencial del 26 de octubre, en dos láminas.
Repaso · Polimorfismo

Un tipo común y cada objeto responde a su manera

Notificacion.java
class Notificacion {    void enviar(String mensaje) {        System.out.println("Notificación: " + mensaje);    }}
Email.java
class Email extends Notificacion {    @Override    void enviar(String mensaje) {        System.out.println("Email: " + mensaje);    }}
SMS.java
class SMS extends Notificacion {    @Override    void enviar(String mensaje) {        System.out.println("SMS: " + mensaje);    }}
Main.java
public class Main {    public static void main(String[] args) {        Notificacion[] notificaciones = {            new Email(), new SMS(), new Email()        };         for (Notificacion n : notificaciones) {            n.enviar("Hola mundo");        }    }}
Consola
Email: Hola mundo
SMS: Hola mundo
Email: Hola mundo
Un arreglo de la madre y un for, sin ningún if que pregunte el tipo: así se ve el polimorfismo.
Repaso · Los dos tipos

La variable decide qué puedes llamar; el objeto, qué se ejecuta

  • Animal a = new Perro(...) es válido: un Perro es un Animal.
  • Al correr, la JVM ejecuta la versión del objeto real: enlace dinámico.
  • Siempre @Override: si escribes mal el nombre, el compilador avisa.
Con esto basta para entender las interfaces.

Interfaces y herencia múltiple

⏱ ~28 min
¿Y si dos clases no comparten padre pero deben hacer lo mismo?
Interfaces · El problema

Una Sirena también avisa, pero no es una Notificacion

  • Email y SMS heredan de Notificacion.
  • Una Sirena también «envía un aviso», pero no tiene sentido que sea una Notificacion ni que herede de Email.
  • Y una clase solo puede tener una madre.
  • Queremos el polimorfismo sin obligar a nadie a heredar.
Necesitamos algo que diga qué debe saber hacer una clase, sin decir cómo.
Interfaces · La idea

Una interfaz es un contrato: dice qué, no cómo

Notificador.java
interface Notificador {    void enviar(String mensaje);}
  • Solo declara métodos: sin cuerpo.
  • La clase firma el contrato con implements y escribe cada método.
  • Los métodos de una interfaz son public; al implementarlos también.
AnalogíaUn contrato de renta: dice qué debe cumplir quien renta, no cómo organiza su casa.
El contrato no tiene código: cada clase pone el suyo.
Interfaces · En código

Email y Sirena cumplen el contrato, sin ser familia

Notificador.java
interface Notificador {    void enviar(String mensaje);}
Email.java
class Email implements Notificador {    @Override    public void enviar(String mensaje) {        System.out.println("Email: " + mensaje);    }}
Sirena.java
class Sirena implements Notificador {    @Override    public void enviar(String mensaje) {        System.out.println("Sirena: ¡" + mensaje + "!");    }}
Main.java
public class Main {    public static void main(String[] args) {        Notificador[] canales = {            new Email(), new Sirena()        };         for (Notificador c : canales) {            c.enviar("Incendio");        }    }}
Consola
Email: Incendio
Sirena: ¡Incendio!
Mismo for, mismo tipo, dos clases que no son familia.

Interfaces · Regla 1

Una interfaz no se instancia: es un tipo, no un objeto

Notificador.java
interface Notificador {    void enviar(String mensaje);}
Main.java
public class Main {    public static void main(String[] args) {        Notificador n = new Notificador();         n.enviar("Hola");    }}
javac
Main.java:3: error: Notificador is
  abstract; cannot be instantiated
  Notificador n = new Notificador();
                  ^
Sí puede ser el tipo de una variable; lo que no se puede es crear un objeto con new.
Interfaces · Regla 2

Quien firma el contrato debe cumplirlo completo

Notificador.java
interface Notificador {    void enviar(String mensaje);}
Email.java
class Email implements Notificador {    void avisar(String mensaje) {        System.out.println("Email: " + mensaje);    }}
javac
Email.java:1: error: Email is not
  abstract and does not override
  abstract method enviar(String)
  in Notificador
Falta enviar(String): sin él, Email no cumple el contrato y no compila.

Herencia múltiple · El problema

Un Pato vuela y nada: ¿le damos dos padres?

  • Volador y Nadador heredan de Animal.
  • Los dos sobrescriben moverse().
  • Un Pato querría ser las dos cosas.
Esta forma de rombo es el problema del diamante.
Herencia múltiple · Java dice que no

En Java una clase tiene un solo extends

Animal.java
class Animal {    void moverse() {        System.out.println("Se mueve");    }}
Volador.java
class Volador extends Animal {    @Override    void moverse() {        System.out.println("Vuela");    }}
Nadador.java
class Nadador extends Animal {    @Override    void moverse() {        System.out.println("Nada");    }}
Pato.java
class Pato extends Volador, Nadador {}
javac
Pato.java:1: error: '{' expected
class Pato extends Volador, Nadador {
                          ^
Java prohíbe la herencia múltiple de clases.
Herencia múltiple · Por qué

¿Qué moverse() heredaría Pato?

Clasemoverse() imprime
VoladorVuela
NadadorNada
Pato (hereda de las dos)¿Vuela o Nada?
Con dos versiones heredadas del mismo nombre, el compilador no puede elegir por ti. Java lo evita prohibiendo el segundo extends.
Ese choque entre dos versiones es el problema del diamante.
Herencia múltiple · La salida

Una clase, muchas interfaces

  • Una clase solo puede tener un extends.
  • Pero puede tener todos los implements que necesite.
  • Una interfaz no trae código: no hay versiones que choquen.
De clases no; de interfaces sí.
Herencia múltiple · En código

Pato implementa las dos y se usa como cada una

Volador.java
interface Volador {    void volar();}
Nadador.java
interface Nadador {    void nadar();}
Pato.java
class Pato implements Volador, Nadador {    @Override    public void volar() {        System.out.println("El pato vuela");    }     @Override    public void nadar() {        System.out.println("El pato nada");    }}
Main.java
public class Main {    public static void main(String[] args) {        Pato pato = new Pato();         Volador v = pato;        Nadador n = pato;         v.volar();        n.nadar();    }}
Consola
El pato vuela
El pato nada
El mismo objeto sirve como Volador y como Nadador.
Herencia múltiple · Mismo método

Si las dos interfaces piden el mismo método, se escribe una vez

Volador.java
interface Volador {    void moverse();}
Nadador.java
interface Nadador {    void moverse();}
Pato.java
class Pato implements Volador, Nadador {    @Override    public void moverse() {        System.out.println("El pato vuela y nada");    }}
Main.java

El pato vuela y nada
El pato vuela y nada
No hay choque: las dos piden moverse() y Pato lo escribe una sola vez.
Herencia múltiple · default

Con métodos default, el choque vuelve

Volador.java
interface Volador {    default void moverse() {        System.out.println("Vuela");    }}
Nadador.java
interface Nadador {    default void moverse() {        System.out.println("Nada");    }}
Pato.java
class Pato implements Volador, Nadador {}
javac
Pato.java:1: error: types Volador and
  Nadador are incompatible;
  class Pato inherits unrelated
  defaults for moverse() from types
  Volador and Nadador
Una interfaz puede traer un default con cuerpo; si dos traen el mismo, Java obliga a elegir.
Herencia múltiple · default, la salida

Pato decide con Volador.super y Nadador.super

Volador.java
interface Volador {    default void moverse() {        System.out.println("Vuela");    }}
Nadador.java
interface Nadador {    default void moverse() {        System.out.println("Nada");    }}
Pato.java
class Pato implements Volador, Nadador {    @Override    public void moverse() {        Volador.super.moverse();        Nadador.super.moverse();    }}
Main.java
public class Main {    public static void main(String[] args) {        new Pato().moverse();    }}
Consola
Vuela
Nada
La clase sobrescribe moverse() y elige a quién llamar.

Excepciones · Qué es

Una excepción es un objeto que avisa que algo salió mal

  • Cuando algo falla al correr, Java crea un objeto con el tipo de error y un mensaje.
  • Ese objeto se lanza: sube buscando a alguien que lo atrape.
  • Si nadie lo atrapa, llega hasta main y el programa termina con la traza.
AnalogíaUna alarma de incendio: alguien la activa en un piso y suena hasta que alguien la atiende. Si nadie la atiende, se evacua todo el edificio.
Excepción no es un error de compilación: el programa compiló y truena al correr.

Excepciones · try-catch

try-catch: intenta, y si falla, atrapa

Main.java
public class Main {    public static void main(String[] args) {        String texto = "dos";        try {            System.out.println("Convirtiendo...");            int piezas = Integer.parseInt(texto);            System.out.println("Piezas: " + piezas);        } catch (NumberFormatException e) {            System.out.println("Eso no es un número: " + texto);        }        System.out.println("El programa sigue");    }}
  • En try va el código que puede fallar.
  • Si una línea lanza la excepción, las que siguen dentro del try se saltan (la gris).
  • Corre el catch del tipo que coincide.
  • Después, el programa sigue normal.
Consola
Convirtiendo...
Eso no es un número: dos
El programa sigue
Mismo error que hace un momento, pero ahora el programa no termina.
Excepciones · El menú que no truena

Pedir la opción hasta que sea válida

Main.java
import java.util.Scanner; public class Main {    public static void main(String[] args) {        Scanner sc = new Scanner(System.in);        int opcion = 0;        boolean valida = false;        while (!valida) {            System.out.print("Opción (1 a 3): ");            try {                opcion = Integer.parseInt(sc.nextLine());                if (opcion >= 1 && opcion <= 3) {                    valida = true;                } else {                    System.out.println("Solo de 1 a 3");                }            } catch (NumberFormatException e) {                System.out.println("Escribe un número");            }        }        System.out.println("Elegiste la " + opcion);    }}
Consola
Opción (1 a 3): dos
Escribe un número
Opción (1 a 3): 7
Solo de 1 a 3
Opción (1 a 3): 2
Elegiste la 2
  • Se lee la línea completa con nextLine() y se convierte con parseInt.
  • El catch atrapa el texto que no es número; el if, el número fuera de rango.
  • El while vuelve a preguntar.
Este es el menú que pide el proyecto: escriban lo que escriban, no truena.
Excepciones · Error común

El catch vacío esconde el problema

Main.java
public class Main {    public static void main(String[] args) {        String texto = "dos";        int opcion = 0;        try {            opcion = Integer.parseInt(texto);        } catch (NumberFormatException e) {        }        System.out.println("Elegiste la " + opcion);    }}
Consola
Elegiste la 0
  • Compila y no truena, pero nadie se entera de que el dato era malo.
  • opcion se queda en 0 y el programa sigue como si nada.
  • En el catch siempre haz algo: avisa al usuario o vuelve a preguntar.
Un programa que truena se arregla; uno que falla en silencio, no se nota.
Excepciones · Antes

Un constructor que solo imprime «error» no protege nada

Producto.java
public class Producto {    private String nombre;    private int precio;     public Producto(String nombre, int precio) {        if (precio <= 0) {            System.out.println("Error: precio inválido");        }        this.nombre = nombre;        this.precio = precio;    }     public int getPrecio() {        return precio;    }}
Main.java
public class Main {    public static void main(String[] args) {        Producto p = new Producto("papas", -18);        System.out.println("Cobro: $" + p.getPrecio());    }}
Consola
Error: precio inválido
Cobro: $-18
Avisó, pero el producto se creó con precio -18 y la máquina cobra eso.
Excepciones · throw

throw: la clase se niega a crear un objeto inválido

Producto.java
public class Producto {    private String nombre;    private int precio;     public Producto(String nombre, int precio) {        if (precio <= 0) {            throw new IllegalArgumentException("Precio inválido: " + precio);        }        this.nombre = nombre;        this.precio = precio;    }     public int getPrecio() {        return precio;    }}
Main.java
public class Main {    public static void main(String[] args) {        Producto p = new Producto("papas", -18);        System.out.println("Cobro: $" + p.getPrecio());    }}
Consola
Exception in thread "main"java.lang.IllegalArgumentException:    Precio inválido: -18  at Producto.<init>(Producto.java:7)  at Main.main(Main.java:3)
Con throw el producto con precio -18 nunca existe. IllegalArgumentException significa «me pasaste un argumento que no acepto».
Excepciones · Quién atrapa

La clase lanza; quien la usa atrapa

Main.java
public class Main {    public static void main(String[] args) {        try {            Producto p = new Producto("papas", -18);            System.out.println("Cobro: $" + p.getPrecio());        } catch (IllegalArgumentException e) {            System.out.println("No se pudo: " + e.getMessage());        }        System.out.println("La máquina sigue");    }}
Consola
No se pudo: Precio inválido: -18
La máquina sigue
QuiénQué hace
ProductoRevisa el dato y lanza con throw si no sirve
MainAtrapa con try-catch y decide qué hacer
e.getMessage()Regresa el texto que se puso al lanzar
Producto no sabe si hay un usuario o un menú: solo dice que no. Main decide cómo avisar.

VÁLVULA · finally

finally corre siempre, falle o no

Main.java
public class Main {    public static void main(String[] args) {        try {            System.out.println("Abro la caja");            int piezas = Integer.parseInt("dos");            System.out.println("Piezas: " + piezas);        } catch (NumberFormatException e) {            System.out.println("Dato inválido");        } finally {            System.out.println("Cierro la caja");        }    }}
Consola
Abro la caja
Dato inválido
Cierro la caja
  • Si el try sale bien: try, finally.
  • Si falla: try, catch, finally.
  • Sirve para cerrar lo que abriste: un archivo, un Scanner.
Lo que va en finally pasa en los dos caminos.
